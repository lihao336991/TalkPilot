# TalkPilot 成本项梳理与 MAU 成本预估模板

更新时间：2026-05-04

目标：
- 统一记录 TalkPilot 线上可能产生费用的三方服务、计费口径与触发点。
- 提供一份可填数的成本估算模型，按不同 MAU 分档给出月成本区间。
- 提前列出“下一档规模”会出现的潜在新增成本项与触发阈值，减少被动爆账单。

范围说明（按当前代码实况）：
- Deepgram：实时转写（ASR）
- LLM：review / suggest / session-recap（统一走 Cerebras + Together fallback）
- Azure Translator：翻译（assist-reply），明确不走 LLM
- Supabase：Auth + Database + Edge Functions + Storage（业务后端）
- RevenueCat：订阅聚合与 webhook / reconcile
- Sentry：崩溃与性能追踪
- Apple Developer Program：iOS 上架固定年费
- EAS Build（如使用云构建/发布）：按团队实际使用情况计费

## 1) 成本项梳理

下表用于“服务 -> 费用驱动 -> 触发点 -> 监控方式 -> 降本手段”的统一口径。

### 1.1 主要按量成本（重点盯）

| 成本项 | 用途 | 费用驱动(你填单价) | 触发点/路径（项目内） | 关键监控指标（建议上报） | 可控开关/降本手段 |
|---|---|---|---|---|---|
| Deepgram ASR | 主链路实时转写 | $/转写分钟 | Edge Function `deepgram-token` mint token；客户端 `DeepgramStreamingService` 建 WS 推音频 | 日转写分钟、日会话分钟、WS 重连次数、失败率 | 提高免费配额门槛控制；减少无效推流；断线重连保护；降低模型/参数成本（如可选） |
| LLM（Cerebras） | suggest / review / session-recap | $/1M tokens(in/out) | Edge Functions：`suggest`/`review`/`session-recap` 统一走 `_shared/llm.ts` | 日调用次数、tokens(in/out)、fallback 比例、重试次数、失败率、平均耗时 | 任务分级：短 prompt、强 schema、降低 max_tokens；减少触发频率；限制 session-recap 触发率 |
| LLM（Together） | Cerebras 降级 fallback | $/1M tokens(in/out) | `_shared/llm.ts` 自动路由（LLM_AUTO_PROVIDER_ORDER） | 同上，另加：fallback 命中率 | 降低 fallback 触发（稳定 Cerebras）；避免无意义重试；对 401/429 做熔断 |
| Azure Translator | 翻译（assist-reply） | $/1M chars（或按官方口径） | Edge Function `assist-reply` 固定 `translateWithAzure` | 日翻译次数、字符数、失败率、平均耗时 | 减少翻译触发；合并请求；做缓存（同一句去重）；长文本截断策略 |

### 1.2 基础设施/平台成本（随规模上升）

| 成本项 | 用途 | 费用驱动 | 触发阈值（你填/按套餐） | 关键监控指标 | 可控开关/降本手段 |
|---|---|---|---|---|---|
| Supabase | Auth/DB/Functions/Storage | 月固定 + 用量（DB/egress/函数等） | 关注：MAU、DB 大小、egress、存储 | DB 大小、API/函数请求量、egress、存储增长 | 数据生命周期（清理 turns/reviews）；压缩 payload；缓存；降低函数调用次数 |
| Sentry | 崩溃与性能追踪 | 月固定 + event/trace 用量 | 事件量/采样率达到上限 | error events、performance spans、traces sample 命中量 | 降采样；过滤低价值事件；限制 debug 噪音日志 |

| EAS Build（可选） | 云构建、分发、submit | 月固定或按构建分钟 | CI/团队规模/构建频率上升 | 构建次数、构建分钟、失败率 | 本地/自建 CI；减少无意义构建；复用缓存 |

### 2.2 核心计算公式（建议照搬到表格）

日级用量：
- dau = mau * (dau_over_mau)
- daily_sessions = dau * (sessions_per_dau)
- avg_minutes_weighted = avg_session_minutes * ( (1 - pro_share) + pro_share * pro_minutes_multiplier )
- daily_total_minutes = daily_sessions * avg_minutes_weighted

Deepgram：
- daily_asr_minutes = daily_total_minutes
- daily_asr_cost = daily_asr_minutes * deepgram_price_per_min_usd

翻译（Azure）：
- daily_translation_calls = daily_sessions * translations_per_session
- daily_translation_chars = daily_translation_calls * chars_per_translation
- daily_translation_cost = (daily_translation_chars / 1_000_000) * azure_price_per_1m_chars_usd

LLM：
- daily_llm_calls = daily_sessions * (suggest_per_session + review_per_session + recap_rate_per_session)
- daily_tokens_in = daily_llm_calls * tokens_in_per_call
- daily_tokens_out = daily_llm_calls * tokens_out_per_call
- daily_llm_cost =
  (daily_tokens_in * cerebras_share / 1_000_000) * cerebras_price_in_per_1m_tokens_usd +
  (daily_tokens_out * cerebras_share / 1_000_000) * cerebras_price_out_per_1m_tokens_usd +
  (daily_tokens_in * together_share / 1_000_000) * together_price_in_per_1m_tokens_usd +
  (daily_tokens_out * together_share / 1_000_000) * together_price_out_per_1m_tokens_usd

月级汇总（按 30 天粗估）：
- monthly_variable_cost = 30 * (daily_asr_cost + daily_translation_cost + daily_llm_cost)
- monthly_fixed_cost = supabase_monthly_usd + sentry_monthly_usd + revenuecat_monthly_usd + apple_dev_monthly_usd
- monthly_total_cost = monthly_variable_cost + monthly_fixed_cost

## 3) 下一档潜在成本项及成本（提前预案）

这部分用于回答：当 MAU/使用时长上一个台阶，哪些成本会“突然出现”或“突然抬升”。

### 3.1 Supabase 下一档

可能触发条件（按你当前工程最可能先顶到的顺序）：
- DB 大小增长（turns/reviews/sessions 累积）导致超套餐。
- egress（客户端拉取历史、媒体/日志）导致超套餐。
- Edge Functions 请求量上升导致计费或限流（取决于套餐）。

成本预案（你填）：
- Supabase 下一档套餐名称：
- 下一档月费：
- 超额计费口径（DB/egress/requests）：

处理策略：
- turns/reviews 做生命周期与归档（例如保留最近 N 天/最近 N 个会话的详细 turns）。
- history 下行 payload 做分页与裁剪（只拉必要字段）。

### 3.2 Deepgram 下一档

可能触发条件：
- 日转写分钟数线性上升（最核心可变成本）。
- 网络差导致重复推流/频繁重连，分钟数“虚增”。

成本预案（你填）：
- 当前单价与阶梯价（如有）：
- 目标：把“重复计费系数”控制在 X（例如 <= 1.05）

处理策略：
- 连接失败/重连次数超过阈值时熔断并提示。
- token 预取 + 连接保活策略避免不必要重建连接。

### 3.3 LLM 下一档

可能触发条件：
- review/suggest 在活跃用户增长下触发次数巨大。
- fallback/重试导致 tokens 被放大（尤其是 429/超时）。

成本预案（你填）：
- Cerebras/Together 单价与阶梯价：
- 目标：把“平均 tokens/会话”控制在 X

处理策略：
- 对 suggest/review 增加更严格的触发门槛（例如 turn 太短直接跳过；你当前 review 已对 <4 words 跳过）。
- session-recap 默认降频（只在用户点击/会话结束且时长>阈值时生成）。
- 观察 headers：X-LLM-Attempts / X-LLM-Provider，建立“fallback 告警”。

### 3.4 Azure 翻译 下一档

可能触发条件：
- 翻译文本量增长（字符数）线性上升。
- 同一句反复翻译（无缓存）造成浪费。

处理策略：
- 句子级 cache（同 turnId + direction + targetLanguage 去重）。
- 长文本截断或按句分段。

### 3.5 Sentry 下一档

可能触发条件：
- DAU 上升后 error/trace 事件量爆发。
- 性能追踪采样率过高（当前生产 0.2）。

处理策略：
- 根据 DAU 动态下调 sample rate。
- 过滤已知噪音错误与低价值 breadcrumb。

### 3.6 RevenueCat 下一档

可能触发条件：
- 订阅用户规模/营收达到 RevenueCat 收费阶梯。
- reconcile 频率过高导致额外请求（主要是工程/运维成本，费用按官方口径）。

处理策略：
- 只在必要时 reconcile（购买成功、customer info 更新、用户主动 restore）。
- webhook 幂等与失败重放完善（你已有 billing_webhook_events 作为审计表）。
