# 经验记录

- 2026-04-22：在 `pnpm` 严格依赖布局下，`@sentry/react-native` 的 iOS `Upload Debug Symbols to Sentry` 脚本会直接从项目根执行 `require.resolve('@sentry/cli/package.json')`。如果 `@sentry/cli` 只是其传递依赖而未提升到应用顶层依赖，Xcode Debug/Release 构建都可能在脚本阶段提前失败。当前项目应将 `@sentry/cli` 显式声明到根 `package.json`，不要只依赖传递安装结果。
- 2026-04-22：Supabase Edge Functions 中的 LLM 调用不要开启 `response_format: { type: "json_object" }`。当前项目使用的 provider 兼容层对 `json_object` 支持不稳定，容易出现空响应、字段缺失或 502。统一改为普通文本输出，并在服务端通过 `extractJsonObject()`、标签解析或文本清洗做容错；后续新增或修改 `review`、`suggest`、`assist-reply`、`session-recap` 等函数时都遵守这条规则。
- 2026-05-03：Cerebras 返回 `402` 时优先排查 Billing/额度与 key 所属组织，不要先怀疑 OpenAI-compatible 调用方式。当前项目已在 `supabase/functions/_shared/llm.ts` 收敛"自动路由 + 手动路由"能力：默认 `auto` 会按 `LLM_AUTO_PROVIDER_ORDER`（默认 `cerebras,groq`）尝试 provider，并在可重试错误（如 402/429/5xx 等）时自动 fallback；前端 Debug Overlay 可通过请求头 `x-llm-route-mode` / `x-llm-preferred-provider` / `x-llm-preferred-model` 手动指定 provider/model 做对比测试。
- 2026-05-03：**TitaNet/CoreML 声纹识别跨桶位比较问题**。TitaNet 模型对不同时长输入使用不同的"桶位"（1s/3s/5s/10s preset），每个桶位产出的 embedding 维度虽相同（192D），但语义空间不一致。如果 enrollment 用 5s 录音生成 embedding，实时分析用 1.5s 窗口（映射到 3s 桶位补零），两者虽然都是 192D embedding，但根本不在同一语义空间下比较，cosine similarity 会系统性偏低（无论是不是同一人都只有 0.2~0.4）。**解决方案**：让 enrollment 和实时分析使用相同的桶位——将实时窗口从 1.5s 改为正好 1s（16000 samples，命中原生 1s preset 无补零），同时 enrollment embedding 改为从多个 1s 段取平均。这样才能保证 enrollment 与实时 embedding 在同一语义空间下比较。
- 2026-05-03：**Enrollment 录音无 VAD 裁剪导致 embedding 偏移**。用户录 5s enrollment 时，如果开头/结尾有静音段，这段静音会被原样送入模型生成 embedding。虽然模型内部有归一化，但大量静音帧会稀释有效语音的 mel 谱特征，导致产出的 embedding 不能准确代表说话人特征。**解决方案**：在生成 enrollment embedding 前，用能量检测（如 20ms 帧 RMS 阈值）裁掉头尾静音段，只保留有效语音区间。这能显著提升 enrollment embedding 的质量，让后续相似度比较更有区分度。
- 2026-05-03：**实时声纹稳定化不要只用“连续两次命中”**。在 1s 窗口、500ms 步长的实时声纹场景里，单帧 similarity 会有自然抖动，常见模式是 `unknown -> self -> unknown -> self -> self`。如果稳定化策略只要求“连续两次 self 才输出 self”，就会把这种整体明显偏向本人的序列错误压成 `unknown`，最终把决策权错误让给 Deepgram。**更合适的策略**：采用“强命中直通 + 最近窗口多数表决”，其中 `unknown` 作为中性票而不是否决票。这样像“3 个 self + 2 个 unknown”这种整体明显偏 self 的连续音频，就能稳定输出 `self`，而不会因为前两帧不连续而被误判为 `unknown`。
- 2026-05-03：**实时气泡划分不要让 voiceprint 在词级 run 上主导左右归属**。当 Deepgram 已经给出词级 diarization 和有效 `speaker id` 时，气泡的切段边界与左右归属应优先依赖 Deepgram；voiceprint 更适合作为“是不是我”的辅助信号、auto-lock 信号和 debug 信号。如果让 voiceprint 在每个短 run 上直接覆盖 speaker，容易出现“同一句话前半段在左边、后半段在右边”的破碎体验。更稳妥的做法是：**Deepgram 决定 turn/bubble 边界，voiceprint 只在 Deepgram 缺少有效 speaker 信息时兜底。**
- 2026-05-03：**voiceprint 更适合在“整条气泡提交前”做本人纠正，而不是在短 run 上实时抢方向**。如果目标是“更激进地识别本人”，不要把 voiceprint 放到词级 run 上直接改左右，否则一句话容易被拆成半左半右。更合理的做法是：先让 Deepgram 决定短时切段，再对一个 buffered turn 累积多个 voiceprint 窗口投票；如果整条气泡级别 `self` 票明显多于 `other`，则在 commit 前把整条消息修正为 `self`。也就是 **run 级别保守、bubble 级别激进**。
- 2026-05-03：**当 debug 面板出现“similarity 很高但最终仍是对方”时，要先区分“窗口级信号”和“气泡级结论”**。单个窗口的 similarity 很高（例如 `0.52`）说明这一瞬间强烈像本人，但如果 turn 级 override 仍要求过多自我票数，最终整条气泡可能还是不会翻回 `self`，造成用户强烈困惑。更符合直觉的做法是：对整条气泡记录 `peak similarity`，若出现强 `self` 命中且没有 `other` 票干扰，就允许整条气泡直接翻回 `self`，并同步把 debug trace 的 `voiceprintDecision/source` 更新成最终结论，避免面板和气泡打架。
- 2026-05-03：**Expo/RN 工作区里的 Swift SourceKit 诊断，不一定能立刻识别 Xcode 新接入的 Swift Package。** 即使 `xcodebuild -resolvePackageDependencies` 已经成功拉下并解析了包，编辑器里的单文件 SourceKit 仍可能暂时报 `No such module ...`。这类问题先以 Xcode 工程能否成功 resolve / build 为准，不要急着回退代码；必要时让用户在 Xcode 里重新打开 `xcworkspace/xcodeproj`、等待索引完成后再看诊断。
- 2026-05-03：**当 `ios/` 已经被当作持久化原生壳维护时，不要再让 `rebuild:ios` 这类日常脚本默认执行 `expo prebuild --clean`。** `--clean` 会清空并重建原生目录，容易把手写的 Swift 文件、`xcodeproj` 里的 Swift Package / Build Phase 改动一起抹掉。更稳妥的做法是把“安全同步依赖”和“显式清空重建”拆成两个脚本：例如 `rebuild:ios` 只做 `pod install`，真正危险的重建动作单独命名成 `prebuild:ios:clean`。
- 2026-05-03：**`history` 的离线 recap 与逐条 `review` 不要长期复用廉价默认 LLM 路由。** 这两条链路对输出质量和格式稳定性更敏感，如果继续跟 `suggest` 共享 `auto -> cerebras/groq` 小模型，容易出现“结构勉强合法但内容像乱码/没逻辑”的坏结果，并且 `session-recap` 还会把坏结果持久化到 `sessions.recap` 里长期污染 History。更稳妥的做法是：为 `review` 和 `session-recap` 提供单独的 provider/model 配置（当前约定支持 `REVIEW_LLM_PROVIDER` / `REVIEW_LLM_MODEL` / `SESSION_RECAP_LLM_PROVIDER` / `SESSION_RECAP_LLM_MODEL`），同时在服务端做基础文本质量校验；`session-recap` 需要支持 `force regenerate`，让用户能把旧的坏总结重新生成掉。
- 2026-05-04：**这台 macOS 环境里直接执行 `pod install` 可能因为终端编码不是 UTF-8 而失败。** 现象是 CocoaPods 在启动阶段抛 `Unicode Normalization not appropriate for ASCII-8BIT (Encoding::CompatibilityError)`，并提示 `CocoaPods requires your terminal to be using UTF-8 encoding`。遇到这种情况不要误判为 Podfile 或依赖损坏，先在命令前显式加上 `LANG=en_US.UTF-8` 和 `LC_ALL=en_US.UTF-8` 再执行，例如 `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 npm run pods:ios`。
